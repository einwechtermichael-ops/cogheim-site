Between the Check and the Use

Two crashes this week, one in the engine and one in our own tools, came from the same small gap: the moment between checking that something is safe and actually using it.

Published15 November 2026
CategoryEngine & Tooling
SeriesDev Brief

Header image: Pools, young trees and pale dunes in one of our coastal desert regions, seen from above in the editor. Work in progress.

The bugs that cost the most time are often tiny: a line that looks careful, passes every test, and fails once in a few hundred tries. This week we met two of them. One lives inside Unreal Engine 5.8 and was reported publicly by another studio. The other lived in one of our own editor scripts. They look nothing alike on the surface, but they share one shape, and that shape is worth a post.

The picture at the top is from one of our coastal desert regions, captured in the editor while the tools in this story were busy rebuilding its vegetation. It is work in progress.

The shape: check, then use

Defensive code follows one pattern: before you touch something, check that it is still there. Is the pointer valid? Is the level loaded? If yes, go ahead.

The trap is that "check" and "use" are two separate moments. If anything else in the program can change the answer between those two moments, the check only tells you what was true a moment ago. Programmers call this a time of check to time of use problem. In a game engine, where several threads run side by side and the editor can call back into your own code while it is busy, that moment is wider than it looks.

Case one: a world that disappears mid sentence

Unreal Engine runs game logic on one thread and prepares rendering on another, often a frame apart, so the render thread can still be working on a world the game thread has moved on from.

A developer at another studio reported a crash on Epic's forums on 10 November. Their packaged game, running with hardware ray tracing, switched between three small maps every few seconds as a stress test. After roughly nine hours and about seven hundred map loads, the render thread crashed with a null pointer.

The cause is in a small piece of the engine's Compute Framework that asks, every frame, whether any compute work wants to run after the ray tracing scene is built. To answer, it looks up the world through a weak pointer. A weak pointer is a reference that does not keep its target alive; you are expected to check it before use. The code does check it. Then it reads through it a second time to reach the scene. Each read resolves the pointer on its own. If the game thread destroys the old world in the instant between those two reads, which happens during a map change, the first read says "valid" and the second one finds nothing.

We read the same file in the engine version we build against, and the pattern is there, line for line. The engine only takes that path when ray tracing is enabled, and COGHEIM uses hardware ray tracing for its lighting. The plugin that holds this code is loaded in our editor because other engine features depend on it. We have never seen this crash in our own logs.

Why care about a crash that needs seven hundred map loads? COGHEIM is a persistent world. A single test session rarely changes maps. But servers restart, every player travels from the front end into the world, editors load region after region while building content, and every play session in the editor ends by tearing a world down. A one in seven hundred event, spread over many machines and many hours, is not rare at all.

What we did: we wrote it into our engine watch file with the exact signature to look for, so that if it ever appears, nobody spends a day searching our own code for it. We are not switching ray tracing off to dodge it; that would trade our lighting for a crash we have not seen. The reporter proposed a clean fix: hand the renderer the scene directly instead of the world, so the render thread never touches an object the game thread is free to destroy. That is a good rule well beyond this one file, and it is how we try to write our own systems: the game thread owns gameplay objects, and anything crossing to the render thread is a copy or something with a lifetime the renderer controls.

Case two: a script that called itself

The second crash was ours. This week we rebuilt the vegetation across our world regions, which means opening each region in the editor, regenerating its procedural scatter, waiting for it to settle, and saving only what changed. For dozens of regions that is a job for a Python script, so we wrote one that runs inside the editor as a small state machine. It registers a callback that the editor's interface layer calls after every frame. On each call the script looks at its current state: load the next level, wait, regenerate, wait, save, move on.

The first run crashed within seconds with an assertion deep inside World Partition, the engine's system for streaming a large world in pieces.

The editor log showed the same map load command three times, all on one frame. Loading a large level shows a progress dialog, and to keep that dialog alive the editor keeps ticking its interface. Ticking the interface calls every callback registered on it, including ours. Our script checked its state, saw "load the next level", and started loading. But it only changed its state after the load call returned. So while the first load was still running, the editor ticked, our callback ran again, read the same unchanged state, and started a second load inside the first. Then a third. World Partition, finding itself set up twice for the same world, stopped the editor rather than carry on with damaged state.

Same shape as case one: we checked the state, and before we acted on it the world changed underneath us. Except this time the "other thread" was our own code, called back while it was still busy.

The fix took minutes. The rebuild now runs as separate steps, each one a single command that does one thing to the level already open, with no per frame callback and no map loads from inside a callback. The next run went through dozens of regions without a single repeated load. The rule we took from it is simple: never start something that can tick the editor from inside a tick. If a tick driven script is unavoidable, it marks itself busy and moves to its next state before it starts any long call, not after.

Why this matters for a game like ours

COGHEIM's cities walk. Players live inside moving Striders, and the world around them streams in and out as they travel. That means lots of things are created and destroyed while other systems are still looking at them: rooms, crews, effects, whole pieces of terrain. The habits that catch small gaps like these are the same habits that will keep a moving city stable when it is full of people.

We will not see every bug before it happens. We can learn the shape, write down the signature, and close the gap in our own code first.
