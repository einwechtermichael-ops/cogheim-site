A Name Is Not a Fingerprint

A community bug report about ground collision in a preview build of Unreal Engine is a clean lesson in cache keys, and it touches exactly the kind of terrain COGHEIM generates.

Published18 November 2026
CategoryEngine & Tooling
SeriesDev Brief

Header image: Young trees, reeds and a shallow pool among the dunes of one of our dry regions, captured in the editor. Work in progress.

Some bugs are loud. The editor stops, a dialog appears, and you know where to look. The bugs that cost the most are quiet. Everything runs, every frame draws, and the world is simply wrong in a way nobody notices until a character walks across it.

This week another studio reported one of the quiet kind on Epic's forum, against the Unreal Engine 5.9 Preview. It has not been confirmed by Epic yet, so treat the details as a community report. But the shape of the bug is worth understanding whether or not you ever touch that preview, because it is a mistake every programmer makes at least once: confusing what something is called with what something is.

The picture at the top is from one of our dry regions, captured in the editor this week while the vegetation pass was running. It is work in progress, and it happens to show the thing this post is about: ground.

Ground is expensive to make solid

Drawing a hill is one problem. Making the hill solid, so a boot lands on it, a cart rolls over it and a falling crate stops on it, is another. The physics engine cannot test collisions against a raw list of triangles quickly enough, so before a mesh can be stood on, the engine "cooks" it into a search structure built for fast queries. For a large piece of terrain that cooking takes real time.

So Unreal caches it. When a mesh has been cooked once, the result is stored, and the next time the engine needs collision for the same mesh it reads the stored result instead of cooking again. Every cache needs a key, a short string that says "this stored result belongs to that input". If the key is right, the cache is pure speed. If the key is wrong, the cache hands you a confident, fast, wrong answer.

What the report describes

The report concerns procedural meshes: geometry a game builds while it runs rather than loading from a file. Terrain is the classic case. The studio built many ground tiles at runtime, each with a different shape, each above a size threshold where the engine decides cooking is worth caching.

Every tile came back with the same collision. Traces aimed at one tile hit the surface of another. In their game, characters fell through the world. Clearing the cache did not help, because the next run filled it the same way.

Their reading of the cause is simple. Part of the cache key is an identifier attached to each piece of physics data. In earlier engine versions that identifier was a fresh random value every time the physics data changed. In the preview it is derived from where the object lives instead. For tiles created at runtime with the same settings, "where it lives" looks the same, so the keys match, and the cache believes it has already seen this mesh.

Names and fingerprints

That is the whole lesson in one sentence: a name tells you where something lives, a fingerprint tells you what it is, and a cache key must be a fingerprint.

There are three ways to build that key, and the bug sits neatly between them.

A random value on every change. Always safe, because no two inputs can ever collide. Also wasteful, because two identical meshes never share a cached result, and the cache only helps the exact object that filled it.

A value derived from the object's name or path. Stable and deterministic, which is what build systems love, because the same project produces the same output every time. But it is only correct if the name changes whenever the content changes. For anything generated at runtime, that promise does not hold.

A value derived from the content itself. Hash the vertices and the triangle indices, and the key describes the mesh, not its address. Identical meshes share a result, different meshes never do. The reporting studio's workaround does exactly this: they override the function that supplies the mesh's identity so it hashes the geometry.

The general rule reaches far beyond physics. Shader caches, texture caches, save files, network replication, even the memory systems we design for players all lean on some notion of identity. Whenever a system asks "have I seen this before?", the answer is only as good as the question it actually asks.

Why we read engine source before we believe a headline

COGHEIM's ground code builds terrain tiles as procedural meshes at runtime, with full triangle collision, so a report like this lands squarely in our lane. Our rule is that a report is a lead, never a fact, until we have read the code in the engine version we actually use.

So we did. In the engine version COGHEIM is on today, procedural mesh collision is given a fresh random identifier when it is created and again every time its collision is rebuilt. That is the safe, wasteful option, and it means this bug cannot happen to us on our current version. At our default tile resolution the tiles also sit below the size where the engine bothers caching at all.

Neither of those is a guarantee for the future. Tile resolution is a setting, and raising it would push tiles over the threshold. And a future engine upgrade could carry the new behaviour in with it. So the finding became a written warning on our internal list: before any engine upgrade, and before anyone raises ground resolution, two different tiles must answer a downward trace with two different heights, and a tile rebuilt after the ground under it changes must answer with its new height, not its old one. Our tiles are named by where they sit, so that second case is the one a name based key would get wrong for us. It is a small test that would catch a large, silent failure.

Counting, not feeling

A smaller lesson from the same week. Our editor had been suffering occasional graphics driver crashes, and a driver update went in a week ago. The easy move would be to say "the new driver feels better" and move on. Instead we wrote down every crash with the driver version, video memory in use and what the editor was doing, and waited a full week.

The week ended with one crash, against several in the weeks before. That is encouraging and it is not proof. One crash arrived after a very long editor session, which is its own lesson about restarting tools daily. We will keep counting, because a number written down beats a memory every time.

What the picture shows

Young trees, a stand of reeds and a shallow pool among sand dunes, in one of the dry regions on the disc. It was captured in the editor during a vegetation pass, so the planting, the shoreline and the materials are all still moving. None of the ground in that frame should ever fall out from under a traveller, and the work above is part of how we keep it that way.
