Sixteen Bytes Short

How a small memory layout mismatch inside the editor's Python support can crash Unreal, how we traced it, and what this week's engine news means for a game built in native C++.

Published4 November 2026
CategoryEngine & Tooling
SeriesDev Brief

Header image: One of COGHEIM's walking cities on the sand near the shoreline, seen from above in the editor. Work in progress.

Most of the work that builds COGHEIM never shows up on screen. Before a hull walks across the sand or a deck fills with lamps, someone has written a small script that imports a few hundred meshes, sets their materials and saves them. We drive a great deal of the editor that way, through Python, often through an assistant that sends the scripts for us. It is fast, it is repeatable, and it leaves a written record of exactly what was done.

This week that habit taught us something about how much trust a tool deserves.

A crash with nobody touching anything

This week, the editor on our build machine closed itself. There was no assert, no warning dialog, nothing in the log except the line every developer learns to dread: a fatal error, an access violation, a read from an address that made no sense.

The last thing the editor had done was finish an import script. It reported zero errors. Then, about a minute and a half later, with no further commands sent, the process died.

The crash report gave us the order of the code that was running when it happened. The innermost frames were inside the Python interpreter itself. Above those sat the engine's Python plugin. Above that sat the part of the engine that manages object lifetimes. That is a very particular shape, and it points to one moment in an editor's life: garbage collection.

Two garbage collectors, one handshake

Unreal tracks its own objects and periodically sweeps away the ones nothing uses anymore. Python does the same thing for Python objects, using reference counts and a separate cycle collector for objects that point at each other.

When you run both in one process, they have to cooperate. A Python object can keep an Unreal object alive, and the reverse. So the engine's Python plugin does something sensible: every time Unreal is about to collect garbage, it first asks Python to collect its own. We read that hook in our own engine source. It runs on every collection.

That handshake is where the trouble lives.

Forty bytes, where fifty six were promised

Python's core types have fixed memory layouts. One of them is the object that represents a built in function bound to something. In the version of Python the editor ships with, that object is 56 bytes on a 64 bit Windows machine. The last two slots hold a list of weak references and a pointer used for fast calls.

The engine defines its own variant of that object, so it can attach extra context to functions it exposes to Python. It tells Python that its variant is a kind of built in function, which helps the documentation tools. But the variant only reserves 40 bytes. The two final slots are not there.

Most of the time nobody looks at them. Then the cycle collector runs, finds one of these objects caught in a loop of references, and goes to clear its weak references. It reads 8 bytes from offset 40, which is past the end of the allocation. Whatever happens to sit next in memory gets treated as a pointer.

Another developer reported exactly this on Epic's forum in September, with a careful explanation and a patch that adds the missing fields. An Epic engineer replied that it has been fixed in the engine's main branch. We opened the same files in the engine we build against and found the same 40 byte layout, the same claim to be a built in function, and no space for weak references. The defect is in our engine.

There is one more detail we like. The address our editor tried to read, written out byte by byte, spells a fragment of text. That is what you would expect if the code read the middle of a neighbouring string and treated it as a pointer. It is consistent with the bug. It is not proof, and we are not calling it proof. Until the crash dump is opened with full debug symbols, we record this crash as "probably this, unconfirmed".

Why we write it down instead of guessing

It would be easy to blame our own import script, rewrite it three times and hope. That is how teams lose weeks. Instead we keep a living list of engine warnings that every engine session reads before it starts. Each entry says what was claimed, where we read it, whether it is in our engine, whether it can affect us, and what to do when it shows up. This one now says, in plain terms: if the editor dies inside Python while collecting garbage, suspect this first, save before long scripted batches, restart the editor daily, and do not hold bound engine functions inside Python objects that point at each other.

That last rule costs nothing. It also makes the tools we write a little cleaner.

The engine underneath is moving

The other news this week came from Unreal Fest Tokyo. According to several reports of the keynote, Epic now plans for Unreal Engine 6 to launch its Early Access without Actors, Blueprints or the C++ gameplay framework, moving gameplay to Verse and a new scene system. That contradicts Epic's own June plan, which said Actors and Blueprints would be in early versions of UE6. We have not yet found an Epic page that states the new plan, so we treat it as reported, not confirmed. Epic has also said that 5.9 is coming, with a preview expected next week.

For COGHEIM, the practical answer is calm. Our gameplay is written in native C++ on today's framework, and projects already in production can stay on the Unreal Engine 5 line. We are not starting any port. We will read the 5.9 preview notes when they land, because three of the fixes we are waiting for, including this Python one, may arrive there. Any move to a new engine version goes through our build queue with a full rebuild and a load check, the same as always.

What the news does reinforce is a rule we already follow: keep the important logic in our own C++ modules, behind interfaces we control, rather than spread through visual graphs. If the ground under the engine shifts, that is the code that has to move, and it is easiest to move when it lives in one place.
