The Update That Arrived Overnight

A small editor plugin updated itself this week and stopped C++ builds for other Unreal teams, and here is how COGHEIM keeps its tools from changing under it.

Published1 November 2026
CategoryEngine & Tooling
SeriesDev Brief

Header image: The town on the deck of a walking city, with its industrial hull and the great arch behind. Work in progress, in engine capture.

Most weeks, the interesting engineering story is about something we changed. This week it is about something nobody changed on purpose.

Late on 28 October, developers on Epic's forums began reporting the same failure. They sat down to build their C++ projects, projects that had built fine the night before, and the build stopped in seconds with an error about a module called FabToolset. Nothing in their own code had moved. Within a day there were three separate threads and several more people confirming the same thing.

The cause, as the reporters traced it, was a small one. Fab is the asset marketplace plugin that ships inside Unreal Engine. It can update itself on its own schedule, separately from the engine. Its newest version added one new module, and that module needed a matching entry in a set of build rules that the installed engine ships already compiled. Those precompiled rules did not know about the new module, and an installed engine does not rebuild them. So every C++ build on that kind of engine stopped before it compiled a single line. Blueprint only projects were not affected. Epic had not replied in any of the threads when we checked.

The reported workarounds are blunt: switch the plugin off for the project, or remove the new module from the plugin's own description file. One developer said that uninstalling and reinstalling the plugin cleared it for them a couple of days later.

Why this matters to a team like ours

COGHEIM is built in Unreal Engine 5.8 with its core systems in native C++. Every system that makes a walking city work, from the hull's movement to the systems players will use inside it, goes through a C++ build many times a day. A build that fails for reasons outside the project costs more than the minutes it takes. It costs trust in the build itself, and the first instinct of a tired developer is to go looking for the bug in their own code. That search can eat an evening.

The deeper lesson is that an engine is not one thing. It is a collection of parts that update on different clocks: the engine itself, its bundled plugins, the launcher that installs it, the compiler, the graphics driver, and the tools around them. Pin one of those and the others can still move. On our own build machine we found clear evidence that this marketplace plugin has updated itself once before, weeks after the engine was installed, with its files carrying a newer date than everything around them.

What we checked

We do not take outside reports on trust, and we do not dismiss them either. For every item that lands in our weekly engine watch, we check three things against our own machine.

First, is the problem in our engine? We read the installed engine's files directly. The plugin copy we can read is still the older version with a single module, and the engine's precompiled build rules list that one module and nothing else. That is exactly the gap the reports describe, waiting for the update to arrive.

Second, can it reach our project? Our project does not name the plugin at all, which means it is switched on by default. So yes, it can.

Third, has it already happened to us? Here the logs answer. Every editor session this week reports the older plugin version when it starts up, and our most recent build log ends in success. So today we are on the old plugin, and we are not affected. That is a statement about today, not a promise about tomorrow.

How we handle it

We added this to the standing warnings that every engine session on COGHEIM reads before it starts. The warning says what the failure looks like, word for word, so that nobody mistakes it for a bug in our code. It says what the quickest reversible fix is, and that the fix should be written down and undone once Epic ships a proper repair. And it says to avoid editing files inside the engine install as a first step, because changes there are easy to forget and hard to audit later.

We also added one small habit to our next engine upgrade. When the editor starts on the new engine, the plugin announces its version in the log. We will record that version beside the engine version and the driver version, the same way we already record them beside every crash and every performance number. When something breaks, the first question is always "what changed?", and you can only answer it if you wrote down what you had before.

This is part of a wider rule we work by. A result counts only when a log shows it. "It should compile" is not a build result. "The plugin probably did not update" is not a fact. Our builds all go through one build script that writes a dated log, and our engine checks read those logs instead of trusting memory. It is slower than guessing, and it is much faster than chasing a phantom.

One more from the week

A second report caught our eye for the future. A developer found that the editor can crash while it is recording call stacks, at the moment it loads a library whose internal unwind tables are laid out in a certain chained way. We read that part of the engine source and the loop the report describes is there in our version too. We do not load any third party libraries of our own today, so it cannot reach us yet. But an online game picks up outside libraries over time: voice, anti cheat, analytics. So it went onto the same warning list, with a note to load every new library once with tracing turned on before relying on it.

About the picture

The hero image this week is an in engine capture from our development build: the town that stands on the deck of one of our walking cities, with the industrial hull and its cooling tower on the left and the great arch rising over the middle. It is work in progress. Lighting, materials and dressing are all still moving, and there is a lot of grey still to fill in. But it shows the idea we care about most: a city you can walk through, that is also the thing that walks.

Next time we will be back with whatever the engine throws at us, and hopefully a few more pictures from inside the hull.
