The Bug Our Machine Cannot See

A river simulation that stays bone dry on new graphics drivers, a log full of errors that are not errors, and why a small studio has to test on hardware it does not use.

Published18 October 2026
CategoryEngine & Tooling
SeriesDev Brief

Header image: A galleried atrium inside one of COGHEIM's structures, rings of walkways around a central lift. Engine capture, work in progress.

Most bugs we write about are ones we can open in a file and point at. This week's most interesting one is different. It lives in a place no game studio controls, it only shows up on the newest hardware setups, and the machine we build COGHEIM on is too old to see it at all.

That is the lesson worth sharing: sometimes the most dangerous bug is the one your own desk cannot reproduce.

A river that will not fill

Unreal Engine ships with water systems that can simulate shallow water on a grid: rivers that find their way downhill, pools that fill, lakes that settle against the terrain. To do that, the simulation first needs to know where the ground is. A small shader works out a "bottom contour" for every cell of the grid: take the height the scene was captured from, subtract the measured depth to the terrain, and you have the floor.

In plain arithmetic: height minus depth.

A developer on Epic's forums reported this week that on current NVIDIA drivers under DirectX 12, that one line comes out as height plus depth. The floor of every cell ends up tens of metres in the air. The simulation sees ground far above the water everywhere, concludes there is nowhere for water to sit, and empties the grid. The river stays dry.

They traced the shader through Microsoft's shader compiler and found that the compiled code is correct: it negates the depth value and adds it. The driver then compiles that code a second time for the GPU, and on drivers from the 610 series onward, that second step drops the negation. Older drivers get it right. The same machine running Vulkan gets it right. A small standalone program with no Unreal code in it reproduces the fault. They have filed it with NVIDIA.

Their workaround is a lovely piece of engineering. Instead of writing "height minus depth", write "minus (depth minus height)". Mathematically the two are identical, bit for bit. But the second form leads the compiler to produce a slightly different instruction sequence, one the driver handles correctly. Writing "height plus negative depth" does not help, because the compiler folds it straight back into the failing form.

We want to be clear about what we know. This is a report from another developer, tested by them on an earlier Unreal version, and NVIDIA has not published a response that we have seen. We have not reproduced it ourselves. Which brings us to the interesting part.

Why we cannot see it

COGHEIM is built on Unreal Engine 5.8 with DirectX 12, and the world has water in it: coasts, lakes, rivers, rain. We build with Unreal's water plugins. So this report matters to us.

When we checked, our main development machine turned out to run a graphics driver from two years ago. It sits well below the range the report describes. If one of our rivers misbehaved on a player's new driver, our own machine would show us a perfectly healthy river, and we could spend days looking for a bug in our content that is not there.

That is an uncomfortable thing to discover, and a useful one. Players update drivers, often automatically. A PC game ships into a world of hardware and software combinations that keeps moving after the code is finished. A studio that tests only on its own setup is really testing one point in a very large space.

Here is the plan:

  • Test water on a current driver, or on a second graphics API. Before we trust any shallow water result, it will be checked once on a current NVIDIA driver, or with Vulkan as a cross check.
  • Compare drivers first when results disagree. If a lake is wet on one machine and dry on another, the first question becomes "which drivers?", not "what did we break?"
  • Treat the driver as part of the test setup. The driver version will be written down next to any rendering result, the same way we decided last week to record the build configuration next to every server memory number.

An error that is not an error

The second lesson this week is quieter, and it is about honesty in our own logs.

Our rule for checking that the editor started cleanly includes a simple test: zero lines marked "Error". It is a good rule because it is blunt. Nobody gets to decide that a particular error does not count.

This week a developer reported that one of the editor's built in automation plugins writes a line at Error level every time it sends a correct reply to a client. For example, when a client asks for a feature the server does not offer, the server answers "I don't know that one" and the client politely falls back. Nothing is wrong. The log still says Error.

We opened the plugin's source in the engine we use and found the same behaviour on the same lines. Then we searched our own editor logs and found it had already happened once this week: an "unknown session" error, followed a third of a second later by a fresh session that worked perfectly.

A blunt rule meets a noisy log, and something has to give. The wrong answer is to start skimming past the word Error. The fix we are making is narrower: we list the exact messages that mean "a client asked a question the server answered correctly", by their full text, and every other error from that plugin, especially the one that says the server failed to start, still counts. Verification reports will quote the exact lines they saw instead of a bare count.

Smaller notes from the week

Power of two growth. Unreal stores distance field data for scene objects in buffers sized to the next power of two of the object count. Another developer reported long hitches when streaming dense foliage moved that count back and forth across a boundary, forcing the buffers to be rebuilt. We confirmed the sizing rule in the engine source but have not measured our own counts, so this goes on our watch list, with a budget to set before dense foliage arrives.

Build tools can race. A report describes a race in Unreal's header tool that can make the engine think one of its own modules changed when nothing did. It only bites teams who build the engine from source, which we do not do today.

Why we write these up

The cities of COGHEIM walk across a living world, and a lot of that life is water: steam off a hull, rain across a deck, rivers that should run where the land falls. We would rather learn this week that our own machine cannot see a whole class of water bugs than learn it from a player whose river is dry.

If you build with Unreal's shallow water systems on a recent NVIDIA driver, it is worth ten minutes to check that your water actually holds. And if you have a good way to keep a small team's test machines honest about drivers, we would like to hear it.
